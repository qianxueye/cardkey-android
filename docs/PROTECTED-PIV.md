# Protected PIV manager

The dedicated PIV panel imports previously contact-provisioned enrollment. Select the independently trusted public issuer certificate first, an optional raw signing file second, and the private JSON profile last. Opening another picker retires the previous private profile. The issuer certificate is a public-key and SKI pin container: the importer does not evaluate PKIX, expiry or revocation, choose an authority, or add system trust. No trust is learned from a card response. This consumer supersedes the former API-only manager exclusion for this bounded workflow.

The certificate is one PEM or DER certificate up to 32 KiB. The private UTF-8 JSON is at most 4 KiB, with exactly four unique string fields: `guid` (16-byte hex), `issuer_id` (8-byte hex), `card_public` (97-byte uncompressed valid P-384 point), and `pairing` (eight ASCII digits). The P-384 issuer SPKI and first eight bytes of its SKI must match the profile. Certificate bundles, private-key PEM, missing/duplicate/unknown fields, wrong types, malformed hex and trailing input are rejected. Import readiness does not establish live card identity.

Protected public status, slot/certificate and SSH reads use one finite session. PIN verification, CSR, raw file signing, ECDH and RSA checks use two finite sessions:

1. Recognition authenticates the pinned issuer, enrolled GUID/card key, key confirmation and pairing. It reads protected metadata, data-free PIN status and the required slot without PIN or private commands.
2. The first native session closes. The panel displays authenticated retry facts and collects explicit PIN confirmation.
3. Execution creates a fresh secure context, authenticates the same enrolled identity and rereads retry/slot facts. Differences reject before PIN. Only then does the existing PIV client perform verification or the private operation.

Successful recognition updates only the protected panel's pending PIN state. It does not publish a completed private operation, cryptographic-verification message, export or generic task receipt. Only the second session can publish the requested private operation's result; read-only protected operations retain their ordinary result receipts.

Signature, SSH public-key, CSR and certificate exports capture public output bytes, their real format, operation and slot in the existing ViewModel document owner before opening the save picker. Activity recreation retains that bounded snapshot and one request identifier. Background cleanup still retires the private profile, pairing and PIN inputs. A duplicate or retired picker callback cannot replay a write; cancelled and uncertain output writes keep their corresponding outcomes. No private profile or PIN is saved to restore an export.

Enrolled protected operations accept CONTACT, NFC and UNKNOWN media while retaining the actual medium in the bound session. UNKNOWN does not enable plaintext PIN/PUK or administration. Authenticated `6983` on UNKNOWN returns `CARD_REJECTED` with the original status and stops the operation; it neither establishes exhausted PIN retries nor triggers a retry.

Each scan uses the existing `CardOperationGate`, one `CardSession.run`, one `PivSecureContext`, and one protected `PivClient`. Ordinary commands never serve as fallback. Data-free `63Cx` reports remaining retries without decrement. Authenticated NFC `6983` requires contact recovery. Pairing failure never claims a PIN or PUK effect. Raw signing retains the existing 1 MiB input bound, slot/SPKI checks and local signature verification. CMS, TLS, CA orchestration, management authentication, generation/import, reset and PIN/PUK changes retain their existing contact paths.

A generation binds imports, picker callbacks, immutable operation inputs and recognition receipts. Private input is parsed only after active return from the system picker. An owned picker may preserve its request and public issuer/file preparation across Activity pause, but never an existing private profile. Background, explicit clear, route replacement and terminal operations clear private references; operation-owned PIN and pairing arrays are cleared as well. This is not a guarantee that all runtime copies are zeroized. No secrets enter saved state, logs, clipboard or persistent storage.

Cancellation closes the current channel and prevents later dispatch or success. A missing authenticated final response retains `UNKNOWN`; there is no retry or replay. Recovery inspection remains bound to the original imported GUID and issuer certificate fingerprint. An ordinary read or another profile cannot clear protected uncertainty: reimport the original inputs and explicitly read protected status. Public preparation remains available while private operations are held.

Validation uses synthetic producer-format imports and protocol peers through the actual parser, workflow, manager dispatcher and secure client. Existing protocol fragmentation, GET RESPONSE and contact-only administration regressions remain applicable. APK compilation and JVM tests do not establish APK installation, issuer provisioning, card/RF acceptance or production deployment.
